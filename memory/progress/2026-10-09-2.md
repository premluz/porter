## LOG-20261009-020 — Status for several Claude Code tabs in one window (Q-024)

- Date: 2026-10-09.
- Author: assistant; Prem showed the Bastion window working ("Thinking...") while Porter's row for that chat showed no status.
- Cause: that window has two Claude Code tabs, and Porter showed a window's status only when it had exactly one tab and one session, because a hook event names its session and folder but not its tab. (The Porter window, with one tab, does show Idle in Prem's screenshot, so hooks themselves work.) A session that started before the hooks were turned on sends nothing at all.
- Changed: a session is bound to a tab at its first submitted prompt: of the window's Claude Code tabs, the one that came to the front last (the companion's last-used times; 0.2.0 or later). The binding lasts for the session; ties, missing times, or a session start alone bind nothing; a binding to a tab that has gone is dropped. Whatever is not bound is paired only if exactly one tab and one session remain. The old one-tab rule is unchanged.
- Verified: core 116 tests (7 new: bind to the front tab, survive switching tabs, two sessions in two tabs, no times, tie, session start alone, gone tab, one-tab fallback); one mutation (binding off) fails four of them. Not verified: on real windows.
- Needs from Prem: reload the VS Code windows (companion 0.2.0 times), and a Claude Code session whose prompt is sent after Porter runs; the Bastion chat that is working now started earlier, so it shows Unknown until its next prompt.

## LOG-20261009-021 — Source label; opening a chat no longer lifts it; interaction beats viewing

- Date: 2026-10-09.
- Author: assistant; Prem asked for the source of each chat (Browser, VS Code or App) after the project label, that clicking a chat in Porter not move it to the top, and that the order follow the last interaction, with the last message's time if it can be had.
- Changed: (1) Rows carry a source (browser tab, editor, or app; a Codex thread made in VS Code says VS Code, one made in the app says App) and the detail line reads `(logo) [Project] Source · Status`, with the profile after it for browser chats. (2) Porter remembers the few seconds around each activation it makes, per chat, and ignores last-used times a connector reports inside that span, so the arrival Porter caused is not counted as use, even when the connector keeps repeating the stamp. (3) Chrome scripting now stamps a tab when it comes to the front of Chrome, not on every look, and a tab sitting in a background window has no time. (4) An agent's own signal (a prompt sent, a reply finished: Claude Code hook events) is the last interaction and now outranks a time a tab was merely in front; Codex threads already use Codex's update time. Where no signal exists the viewing time is still the fallback, because a browser gives no time for a message.
- Verified: core 119 tests (3 new, plus the recency rule changed in one test), native-host 73, Mac app 73. Slip: while adding the click tests I overwrote an existing test file (`BridgeTests+Recency.swift`) with a new one; I noticed from the diff, restored it from the repository, and moved my tests into `BridgeTests+OwnActivation.swift`; no test was lost.
- Not verified: the order on real data. Last message time exists only for Codex (its own update time) and for Claude Code sessions that send hook events; Chrome and the desktop apps give none, so those use viewing time or the app's own order.

## LOG-20261009-022 — Labels on hover in the collapsed capsule; the edge drawn by Porter (FACT-029)

- Date: 2026-10-09.
- Author: assistant; Prem asked for tooltips on hover in the collapsed state, and reported again that the capsule's border is missing after collapsing, appears when pressed, and goes when another window takes focus ("it should be all the time").
- Cause of the border (from Prem's description): the glass draws its edge only while its window is active; the non-activating panel is never active in the ordinary way. The three earlier workarounds (rebuild the glass, re-attach the view, force the SwiftUI active state) did not address that and are removed.
- Changed: the edge is a 1 pt stroke Porter draws along the shape (`Palette.glassEdge`), independent of window state. Hovering a dot for 0.35 s shows a glass label beside the capsule with the chat's title and the row's detail line (`ItemDetailLine`, now shared); a tracking area on the panel's view (always active, so it works when Porter is not the active app) reports the pointer, each dot reports its frame, `CapsuleHover` picks the dot and places the label on the screen side, kept on screen. The old system tooltips on the dots are gone, since they do not appear for an inactive app.
- Verified: Mac app 76 tests (3 new: hit test, screen rectangle, label placement on both edges and clamping) and the self-test (the label lays out). Not verified: the hover itself and the edge, since this needs a pointer and eyes (batch O).
